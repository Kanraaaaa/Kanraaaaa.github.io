核心问题：曲谱与歌声的成对数据稀缺是 SVS 领域的关键瓶颈。与 TTS 不同，歌声合成需要 音高轮廓（F0）、音符边界、音符对齐和节拍信息等额外旋律标注。 这些信息的获取成本远高于 TTS 的纯文本对齐。本报告系统梳理从原始音频到可训练数据的完整 pipeline。

数据处理全流程总览

从一首原始歌曲到 SVS 可用的训练数据，需要经过 5 个核心环节。每个环节都有学术界和工业界的不同方案。

Step 1

人声分离（Vocal Separation）

从混合歌曲中分离出干净的人声干声（vocal）和伴奏（accompaniment）。这是从"野外"歌曲制作训练数据的第一步。

学术界方法：
• Demucs（Meta）：混合频谱+波形域的混合 Transformer，目前 SOTA。基于 U-Net 结构，4 分支（2 频谱 + 2 波形）。arXiv 2111.12624
• Spleeter（Deezer）：基于 U-Net 的频谱域分离，轻量快速但精度已被超越
• MDX-Net / UVR：社区驱动的人声分离模型集合，MDX23D 融合多模型
• BS-RoFormer：Band-Split Roformer，频带分割 + 旋转位置编码，分离质量极高

工业界实践：
• SingNet（arXiv 2505.09325）：使用 Demucs 从互联网歌曲中分离人声，构建 3000 小时 in-the-wild 数据集
• DeepSinger（arXiv 2007.04590）：使用 Spleeter 分离网络挖掘的歌声数据
• SongTrans（arXiv 2409.14619）：优化分离工具，无需预处理直接从混合音频转写

关键挑战：分离质量直接影响后续所有步骤。残留伴奏会干扰 F0 估计和对齐。

Demucs ⭐10.4K Spleeter ⭐28.3K UVR-GUI ⭐25.6K MSST (BS-RoFormer)
Step 2

歌词对齐（Lyrics-to-Audio Alignment）

将歌词文本与音频时间轴对齐，得到每个音素（phoneme）的起止时间。这是 SVS 训练数据制作的核心步骤。

歌声对齐 vs 语音对齐的差异：
• 歌声音高变化大，共振峰偏移严重，G2P 规则与语音不同
• 长音、颤音、滑音导致音素边界模糊
• 歌词可能跨语言，需要多语言 G2P
• 音符时长与音素时长耦合，需要同时考虑音乐节拍

学术界方法：
• MFA（Montreal Forced Aligner）：基于 Kaldi 的强制对齐工具，SVS 社区最广泛使用。Opencpop 使用 MFA 进行音素边界标注，但需要用歌声数据重新训练声学模型以适配歌声特性
• DeepSinger 对齐模型：设计专门的歌词-歌声对齐模型，从粗粒度句子级（基于 DTW）到细粒度音素级（基于 CTC/Attention）逐步对齐，完全避免人工标注
• SongTrans（arXiv 2409.14619）：统一歌声转写和对齐方法，自回归模块预测歌词+音符时长+音符号，非自回归模块预测音高和时长，同时完成歌词转写和音符对齐
• STARS（arXiv 2507.06670）：统一框架，同时完成歌声转写、对齐和细化风格标注。分层声学特征处理（帧/词/音素/音符/句），非自回归局部声学编码器
• VocalParse（arXiv 2605.04613）：基于大音频语言模型（LALM）的统一歌声转写。交错提示建模歌词+旋律+词-音符对应关系，CoT 策略先解码歌词作为语义支架
• LyricsAlignment-MTL：多任务学习的歌词-音频对齐，深度学习方法

工业界实践：
• Opencpop：MFA 对齐 + 人工校验修正，100 首歌逐一检查
• GTSinger：专业音乐人员人工标注音素-音频对齐，80.59 小时
• SingNet：自动化 pipeline，分离后自动对齐 + 质量过滤
• OpenVPI/MakeDiffSinger：提供 MFA 对齐工具链，含歌声专用声学模型
• Synthesizer V / ACE Studio：歌手按已知曲谱演唱，曲谱已知只需做时间对齐

MFA ⭐1.9K MakeDiffSinger ⭐145 Lyrics-to-Audio-Alignment ⭐94 lyrics-sync ⭐74 LyricsAlignment-MTL ⭐67 SingingVoice-Auto-Alignment STARS VocalParse SongTrans
Step 3

音高提取与旋律标注（Pitch Extraction & Melody Annotation）

从人声音频中提取旋律信息，生成与歌词对齐的曲谱。这是旋律控制数据的制作核心。

旋律信息包含：
• F0 轨迹（pitch contour）：逐帧基频估计，反映瞬时音高变化
• 音符序列（note sequence）：将连续 F0 量化为离散 MIDI 音符号，含音高和时长
• 节拍信息：BPM 和小节线位置
• 力度信息：音量变化、重音等

F0 估计方法（学术界）：
• PYIN：基于 YIN 的概率扩展，使用半隐藏马尔可夫模型平滑音高轨迹，librosa 内置
• CREPE（ICASSP 2018）：CNN 模型，从频谱直接预测音高概率分布，6 个层级的精度
• SPICE（Google）：自监督音高估计，端到端训练
• FCPE（arXiv 2509.15140）：快速上下文音高估计，Lynx-Net 架构 + 深度可分离卷积，RTF=0.0062，RPA 96.79%
• RMVPE：鲁棒多尺度音高估计

歌声转谱（Singing Transcription）方法：
• ROSVOT（⭐123）：鲁棒歌声转写和 MIDI 提取，端到端模型
• VOCANO（⭐72）：复调音乐中歌声音符转写框架
• Phoneme-Informed（⭐38）：音素信息辅助的音符级歌声转写
• icassp2022-vocal-transcription（⭐158）：伪标签从帧级到音符级的迁移学习
• STARS：统一框架自动提取旋律+对齐+风格标注
• VocalParse：用音频大语言模型实现规模化歌声转写

MIDI 提取专用工具：
• SOME（OpenVPI，⭐702）：Singing-Oriented MIDI Extractor，专门为 SVS 数据制作设计
• Audio-to-MIDI（⭐62）：人声旋律提取到 MIDI
• GAME（OpenVPI）：生成式自适应 MIDI 提取器

CREPE ⭐1.4K FCPE ROSVOT ⭐123 VOCANO ⭐72 SOME ⭐702 Audio-to-MIDI ⭐62 Vocal-Transcription ⭐158 FCPE paper
Step 4

曲谱标注与对齐（Score Annotation & Alignment）

将提取的旋律信息与歌词时间对齐，形成可训练的"曲谱"标注。这里存在三种路线（详见下文"旋律表征方式"章节）。

三条制作路线：

路线 A：人工标注（高精度，高成本）
• 由音乐专家逐音听取并标注 MIDI 音符和边界
• GTSinger：专业人员标注 80.59 小时，含真实音乐曲谱，6 种技巧标注，4 种语言
• Opencpop：录音棚录制 + 人工标注音素和音符边界，100 首中文歌
• JVS-MuSiC：日语多说话人歌声语料，人工标注

路线 B：歌声转谱（自动）（自动，中等精度）
• 用算法从音频自动提取旋律：F0 估计 → 音符量化 → 边界检测 → 节拍追踪
• DeepSinger：完全自动 pipeline，从网络挖掘歌声自动提取曲谱
• SingNet：Demucs 分离 + 自动对齐 + 质量过滤，3000 小时
• STARS / VocalParse：最新自动化转写框架
• OpenVPI/MakeDiffSinger：SOME MIDI 提取 + MFA 对齐，社区工具链

路线 C：已有曲谱对齐（低成本，需要原始曲谱）
• 如果原始歌曲有现成的 MIDI/曲谱文件，只需做曲谱-音频时间对齐
• RMSSinger（arXiv 2305.10686）：使用真实音乐曲谱，消除繁琐的手动音素级 mel-note 对齐
• Synthesizer V / ACE Studio：歌手按已知曲谱演唱，曲谱已知只需时间对齐
• 商业声库制作：标准做法——让歌手按给定曲谱演唱

GTSinger Opencpop DeepSinger SingNet RMSSinger Opencpop data ⭐237
Step 5

演唱技巧与风格标注（Technique & Style Annotation）

高质量 SVS 需要标注演唱技巧（颤音、滑音、气息、真假声等）和风格信息。

技巧标注方法：
• GTSinger：标注 6 种演唱技巧（混声、假声、气声、颤音、滑音、怒音），覆盖 4 种语言
• TechSinger（arXiv 2502.12572）：开发技巧检测模型自动标注音素级技巧标签，7 种技巧 5 种语言
• STARS：统一框架自动提取细化风格标注（情感、节奏）

风格标注方法：
• StyleSinger：残差量化模块捕获多样风格特征
• StylePitcher（arXiv 2510.21685）：生成风格跟随的音高曲线
• BERT 语义嵌入：引入歌词语义信息增强表达力
• Muse（arXiv 2601.03973）：116k 合成歌曲自动生成歌词和风格标签

旋律表征方式分类

不同 SVS 系统对"曲谱"的表示和处理方式存在根本差异。将原来 15 种细分方式按旋律信息来源和表示形式合并为 4 大类， 更清晰地展现设计空间和选型依据。

A

A. 显式符号曲谱类（Symbolic Score）

用 MIDI 音符 / 小节符号 / 词级曲谱等人类可读的符号表示旋律

核心特征：旋律信息以人类可读、可编辑的符号形式输入——MIDI 音符序列、词级曲谱、 小节级符号记谱等。模型接收的是离散的、结构化的音乐信息。

子类差异：
• 精细音素级（原①）：每个音素对应 MIDI 音符号+精确时长，三重对齐。标注成本极高。
• 词级真实曲谱（原②）：RMSSinger 方案，音符基于词而非音素，免去音素级标注
• MIDI+模型预测（原③）：输入 MIDI 音符序列，模型内部预测音素时长和连续 F0
• 离散化 MIDI+音高 token（原⑤）：MIDI 和 F0 同时离散化为 token，适配编解码 LLM
• 小节级符号曲谱（原⑫）：BACH/HNote 方案，小节级 tokenization，人类可编辑

优点：控制精确、可解释、可编辑、可移植。
缺点：需要曲谱数据（标注成本高或需要 MIR 转谱）；对用户有乐理要求。

XiaoiceSing / HiFiSinger / DiffSinger：精细音素级曲谱
RMSSinger（arXiv 2305.10686）：词级真实曲谱，免去音素级标注
SoulX-Singer（arXiv 2602.07803）：MIDI score-conditioned 模式
DiffSinger (OpenVPI)：MIDI + Variance 模型预测音高/能量/气息
NNSVS / Sinsy：基于 MIDI 的 SVS 工具链
TokSing / CoMelSinger：离散化 MIDI+音高 token，适配编解码 LLM
BACH（arXiv 2508.01394）：小节级符号曲谱，小模型超越 Suno
HNote（arXiv 2509.25694）：十六进制编码 + 32 单位小节框架
B

B. 连续 F0 轨迹类（Continuous Pitch Contour）

直接用或从参考音频提取 F0 轨迹（含归一化变体）作为旋律条件

核心特征：旋律信息以连续的逐帧 F0 轨迹表示，保留颤音、滑音等连续音高细节。 可以直接输入 F0，也可以从参考音频中提取 F0（含归一化处理）。

子类差异：
• F0 直接输入（原④）：逐帧 F0 轨迹直接作为条件，保留全部连续音高细节
• 归一化 F0（原⑬）：F0 归一化为相对音高 / MIDI 区间，消除绝对音高偏差，可跨歌手迁移
• 参考音频 F0 引导（原⑦⑩）：从参考音频提取 F0→离散化为旋律 token，用于翻唱/旋律克隆

优点：保留连续音高细节（颤音/滑音）；归一化后可跨歌手迁移；参考音频方式用户门槛低。
缺点：F0 提取精度影响生成质量；直接输入 F0 的用户门槛较高。

SoulX-Singer（arXiv 2602.07803）：F0 melody-conditioned 模式
StylePitcher（arXiv 2510.21685）：生成风格跟随的 F0 曲线
YingMusic-Singer（arXiv 2512.04779）：参考音频旋律引导，零样本
Pushing the Frontier（arXiv 2607.20253）：two-level melody module 提取+离散化 F0
Qwen-Music（arXiv 2607.11699）：归一化旋律 + Melody-CoT 规划
Seed-Music（arXiv 2409.09214）：多模态旋律输入 + 旋律编辑
C

C. 学习型语义 token 类（Learned Semantic Tokens）

VAE/DCAE 编码器将音频量化为语义 token，隐式包含旋律/节奏/和弦/编排

核心特征：不使用手工设计的 MIDI/符号曲谱，而是让 VAE/DCAE/编解码器自动学习 如何将音频压缩为保留结构信息的语义 token。旋律信息隐式编码在 token 序列中。

子类差异：
• 5Hz/25Hz 语义 codes（原⑮）：ACE-Step 1.5 / Qwen-Music 方案，音频→VAE 量化→语义 token
• 分层 token（原⑪）：LeVo 2 / SketchSong 方案，混合 token→分轨 token 的分层建模
• 旋律 CoT 规划（原⑨）：Qwen-Music 方案，先用 LM 规划旋律 token 再生成歌曲

优点：无需 MIDI/曲谱标注，直接从音频到音频；语义 codes 可复用；天然适配大模型范式。
缺点：旋律控制不透明（隐式编码）；需要大规模训练数据学习编码；不适合精确旋律控制。

ACE-Step 1.5（GitHub ⭐11.9K）：5Hz semantic codes + DiT + Cover 模式，audio_cover_strength 控制结构保留
Qwen-Music（arXiv 2607.11699）：25Hz Music Semantic Tokens + Melody-CoT + 500 万小时训练
LeVo 2（arXiv 2606.30642）：分层 LeLM（mixed→vocal+accompaniment）+ 审美引导
SketchSong（arXiv 2606.03169）：sketch tokens + 四轨建模（人声/贝斯/鼓/其他）
Pushing the Frontier（arXiv 2607.20253）：8-codebook RVQ + hybird-LM + FullDiT
D

D. 无旋律输入 / 多模态融合类（No Melody / Multi-modal Fusion）

仅用歌词/文本生成（无旋律控制），或同时接受多种来源融合控制

核心特征：不要求显式的旋律输入，模型自行决定旋律；或者接受多种输入源 （曲谱+音频+文本+语音提示），在模型内部融合为统一表征。

子类差异：
• 纯歌词/文本生成（原⑥）：YuE/DiffRhythm/Suno 方案，模型自行生成旋律
• 统一语音/歌声模型（原⑧）：UniVoice 方案，旋律条件在歌声模式强约束、语音模式弱约束
• 多模态融合（原⑭）：Seed-Music 方案，曲谱/音频/文本/语音多源融合

优点：用户门槛最低；多模态融合灵活度最高。
缺点：纯歌词方式无法精确控制旋律；多模态融合训练复杂。

YuE（arXiv 2503.08638）/ DiffRhythm（arXiv 2503.01183）/ Suno：纯歌词→完整歌曲
UniVoice（arXiv 2606.05852）：统一语音/歌声，旋律条件门控
Seed-Music（arXiv 2409.09214）：多模态输入（曲谱+音频+文本+语音）+ 旋律编辑

四大类旋律表征对比

类别 旋律信息来源 控制精度 用户门槛 标注/数据成本 适配范式 代表系统
A. 显式符号曲谱 MIDI / 符号曲谱 高~最高 中~高 高（需曲谱） 传统 SVS / 扩散 DiffSinger, SoulX-Singer, RMSSinger, BACH, TokSing
B. 连续 F0 轨迹 F0 轨迹 / 参考音频 高 中（直接） / 低（参考） 中（F0 提取） 传统 SVS / 零样本 SoulX-Singer, YingMusic-Singer, Qwen-Music, Pushing Frontier
C. 学习型语义 token VAE/DCAE 编码 中（隐式） 低 低（自动） 大模型 / LLM ACE-Step 1.5, Qwen-Music, LeVo 2, SketchSong
D. 无旋律/多模态 歌词 / 多源融合 无~高 零~低 低 歌曲生成 LLM YuE, Suno, Seed-Music, UniVoice
选型洞察：
  • A 类（符号曲谱）是传统 SVS 的主流，控制精确但需要曲谱数据——适合有精标数据的场景
  • B 类（F0 轨迹）是 A 和 C 的桥梁——既保留连续音高细节，又可通过参考音频降低用户门槛
  • C 类（语义 token）是 2025-2026 年的新趋势——不需要曲谱标注，但需要大规模数据训练编码器
  • D 类（无旋律/多模态）面向端到端歌曲生成，不适合需要精确旋律控制的 SVS 场景
  • 趋势：从 A（精确但昂贵）→ B（灵活但仍需 F0）→ C（自动但隐式）演进，D 是另一条路线（自由但不可控）

数据路线分析：几百小时精标够不够？

针对用户实际情况——手里有几百小时人工精标曲谱数据，想做基于曲谱的 SVS 模型—— 分析应该走什么数据路线。

核心矛盾：几百小时精标曲谱在传统 SVS 范式下是够用的（Opencpop 3.6h、GTSinger 80h、M4Singer 50h）， 但在当前大模型+大数据的范式下，与 SoulX-Singer（42,000h）、Qwen-Music（500 万小时）相比差距巨大。 需要判断：是坚持曲谱路线扩展数据，还是转向语义 token 路线？

三条可选路线分析

路线一：MIR 转谱扩展数据（保持 A 类符号曲谱表征）

思路：用 MIR 工具从大量野外歌曲自动提取曲谱，扩展现有几百小时精标数据到数千甚至上万小时。

Pipeline：原始歌曲 → 人声分离（Demucs）→ 歌词对齐（MFA）→ MIDI 提取（SOME）→ 质量过滤 → 与精标数据混合训练

优势：
• 保持精确的旋律控制（A 类表征的核心优势）
• 可复用现有精标数据，精标做高质量子集，自动标注做大规模子集
• 工具链成熟（OpenVPI/MakeDiffSinger + SOME + MFA）
• 增量可控：先自动标注 1000h，验证质量后再扩展

风险：
• MIR 转谱精度有上限（F0 估计误差、音符边界不准），自动标注数据有噪声
• 大规模扩展可能需要 3000h+ 才能接近 SoulX-Singer 水平
• 仍然是 A 类表征，在大模型范式下可能不如 C 类灵活

适用条件：如果核心需求是精确旋律控制（用户可编辑 MIDI 曲谱），这是必选路线。

路线二：转向 C 类语义 token 表征（放弃显式曲谱）

思路：不要求曲谱标注，用 VAE/DCAE 编码器自动从音频学习语义 token， 旋律信息隐式编码在 token 中。

Pipeline：原始歌曲 → 人声分离 → VAE 编码为语义 token → 训练 LLM/DiT → Cover 模式控制结构

优势：
• 不需要曲谱标注，任何歌声音频都可用——数据量可轻松到万小时级
• 天然适配大模型范式（LLM + DiT）
• Cover 模式可从参考音频提取结构信息，无需 MIDI 输入
• 有成熟参考：ACE-Step 1.5、Qwen-Music

风险：
• 丧失精确旋律控制——用户无法编辑 MIDI 曲谱来指定"这个音唱 C5 持续半拍"
• 旋律信息是隐式的，调试和可解释性差
• 需要大规模数据训练编码器（ACE-Step 用了 Muse 116K 首，Qwen-Music 用了 500 万小时）
• 几百小时精标数据在这个路线下用不上（不需要曲谱标注）

适用条件：如果核心需求是大规模生成 + 零样本克隆而非精确曲谱控制，可考虑此路线。

路线三：混合路线（A 类精标 + B 类 F0 + 自动扩展）

思路：不走向 C 类，而是在 A/B 类框架内解决数据问题—— 精标数据做核心训练，自动标注数据做扩展，F0 轨迹做旋律补充。

Pipeline：
① 精标子集（几百小时）：人工标注曲谱，训练高质量基础模型
② 自动扩展子集：MIR 转谱（Demucs→MFA→SOME）自动标注，质量过滤后混合训练
③ F0 补充：对无曲谱的歌声数据，提取 F0 轨迹作为旋律条件（B 类表征），不要求 MIDI
④ 课程学习：先用精标数据训练，再用自动标注数据微调扩展

优势：
• 兼顾精确控制和数据规模
• 精标数据不浪费——作为高质量种子数据
• F0 路线（B 类）不要求完整曲谱，降低自动标注门槛
• 可渐进式扩展：先几百小时精标→加 1000h 自动曲谱→加 3000h F0 条件

风险：
• 混合不同质量的数据需要仔细的质量加权
• A 类和 B 类表征在一个模型中共存，需要设计统一的条件接口

适用条件：如果既要精确旋律控制又要大规模数据，这是最务实的路线。

推荐：路线三（混合路线）
  • 阶段一（立即启动）：用几百小时精标数据训练基础 SVS 模型（A 类表征，DiffSinger/SoulX-Singer 架构）， 验证模型质量和曲谱控制精度。这个阶段的数据量与 GTSinger（80h）/ M4Singer（50h）同级，完全够用。
  • 阶段二（数据扩展）：用 OpenVPI 工具链（Demucs→SOME→MFA）自动转谱扩展到 1000-3000h。 精标数据做高质量子集，自动标注做大规模子集，质量过滤+课程学习混合训练。
  • 阶段三（F0 补充+零样本）：对无法自动转谱的低质量数据，提取 F0 轨迹作为 B 类旋律条件。 参考 SoulX-Singer 双模式设计（MIDI+F0），逐步引入零样本克隆能力。
  • 不建议立即转向 C 类：几百小时精标数据在 C 类路线下用不上（不需要曲谱）， 且 C 类需要数万小时数据才能训练好编码器。C 类更适合作为长期方向， 等数据规模上来后再考虑。

端到端数据制作流程案例

以下系统不仅提出了 SVS 模型，还公开了完整的训练数据制作 pipeline。这些案例对于自建数据 pipeline 的团队具有直接参考价值。

DeepSinger：从网络挖掘到训练数据的全自动 Pipeline（arXiv 2007.04590, KDD 2020）

DeepSinger 是首个完全从网络挖掘训练数据的 SVS 系统，其数据 pipeline 开创了自动化数据制作的范式。

完整 Pipeline 步骤：
① 数据爬取：从音乐网站（如 YouTube、Bilibili）爬取歌曲音频和对应歌词
② 人声分离：使用 Spleeter 分离人声和伴奏
③ 歌词对齐：设计专门的歌词-歌声对齐模型，从粗粒度句子级到细粒度音素级逐步对齐：   • 句子级：基于 DTW（动态时间规整）对齐歌词句子与音频
  • 音素级：基于 CTC 的对齐模型，在句子级基础上细化到每个音素
④ 数据过滤：多维度自动过滤——对齐置信度、音高合理性、音频质量
⑤ 歌声建模：Feed-forward Transformer 直接从歌词生成线性频谱图，Griffin-Lim 合成波形

关键创新：歌词对齐模型完全避免人工标注，从 89 个歌手、3 种语言（中文/粤语/英语）的网站数据中自动构建了约 92 小时训练集。

参考价值：DeepSinger 的 pipeline 至今仍是大规模自动数据制作的主流方案。SingNet 等后续工作在其基础上用更好的工具（Demucs 替代 Spleeter）扩展到 3000 小时。

arXiv 2007.04590 Demo Page

SoulX-Singer：42000 小时对齐数据的工业级 Pipeline（arXiv 2602.07803, 2026）

SoulX-Singer 是目前已知最大规模的开源 SVS 训练数据（42000+ 小时）， 支持普通话/英语/粤语三种语言，其数据 pipeline 代表了工业级标准。

数据特点：
• 42,000+ 小时对齐训练数据（人声+歌词+音符）
• 支持MIDI 曲谱（score-conditioned）和F0 旋律（melody-conditioned）双模式
• 跨语言音色保留，解耦音色与内容
• 构建了 SoulX-Singer-Eval 专用零样本评估基准（严格训练-测试分离）

旋律表征方式：同时支持两种——
  • Score-conditioned：输入 MIDI 音符序列，模型处理为内部表示
  • Melody-conditioned：输入逐帧 F0 轨迹，保留连续音高细节

工业级特性：
• 零样本泛化：无需微调即可生成未见歌手的声音
• 歌词编辑：修改歌词同时保持自然韵律
• SVC 变体（SoulX-Singer-SVC）：无需歌词转录或 MIDI 输入，直接音频到音频转换

参考价值：对于"曲谱歌声合成+歌声克隆"目标，SoulX-Singer 是最匹配的开源参考系统。其 42K 小时数据的 pipeline 虽未完全开源，但从论文可推断采用了大规模自动标注（分离+对齐+MIDI提取+质量过滤）。

arXiv 2602.07803 GitHub ⭐838 HuggingFace Model

OpenVPI/MakeDiffSinger：社区驱动的端到端数据制作工具链（GitHub ⭐145）

MakeDiffSinger 是唯一完全开源、可直接使用的 SVS 数据制作 pipeline，由 OpenVPI 社区维护，专为 DiffSinger 设计但通用性较强。

完整工具链：
• MakeDiffSinger（⭐145）：数据集构建 pipeline，从音频到 DiffSinger 训练格式
• SOME（⭐702）：Singing-Oriented MIDI Extractor，从人声音频提取 MIDI
• OpenUtau（⭐4.1K）：开源编辑器，可视化检查和修正标注
• SingingVocoders：歌声专用声码器集合
• GAME：生成式自适应 MIDI 提取器（改进 SOME）

典型流程：
① 人声分离（Demucs/UVR）
② SOME 提取 MIDI（从人声自动提取音符+音高+时长）
③ MFA 强制对齐（音素边界，需歌声声学模型）
④ MakeDiffSinger 格式转换（生成训练用标注文件）
⑤ OpenUtau 人工校验和修正

参考价值：对于想快速搭建 SVS 数据 pipeline 的团队，这是最佳起点——所有工具开源、有文档、有社区支持。SOME 专为 SVS 数据制作设计，是最实用的 MIDI 提取工具。

MakeDiffSinger ⭐145 SOME ⭐702 DiffSinger ⭐3.2K

SingNet：3000 小时 in-the-wild 数据制作 Pipeline（arXiv 2505.09325, 2025）

SingNet 构建了 3000 小时的 in-the-wild 歌声数据集，展示了从互联网歌曲到可训练数据的完整自动化 pipeline。

Pipeline 步骤：
① 数据采集：从互联网获取 sample packs 和歌曲
② 人声分离：使用 Demucs 从混合音频中分离人声
③ 自动对齐：自动歌词-音频对齐 + 质量过滤
④ 预训练模型：基于分离数据预训练 Wav2vec2、BigVGAN、NSF-HiFiGAN
⑤ 基准实验：在 ALT（自动歌词转录）、神经声码器、SVC 上验证

关键贡献：开源了预训练模型（Wav2vec2 for singing、BigVGAN vocoder、NSF-HiFiGAN），可直接用于下游任务。

参考价值：展示了如何用现代工具（Demucs + 自动对齐 + 质量过滤）大规模扩展数据制作。3000 小时远超 DeepSinger 的 92 小时。

arXiv 2505.09325

STARS：统一歌声转写+对齐+风格标注框架（arXiv 2507.06670, 2025）

STARS 是首个统一同时完成歌声转写、对齐和细化风格标注的框架。

统一标注能力：
① 精确音素-音频对齐（phoneme-audio alignment）
② 鲁棒音符转写和时间定位（note transcription & temporal localization）
③ 表达性演唱技巧识别（vocal technique identification）
④ 全局风格刻画（emotion and pace characterization）

架构特点：分层声学特征处理，跨越帧/词/音素/音符/句子五个层级。非自回归局部声学编码器实现结构化分层表示学习。

参考价值：代表了数据标注自动化的最新趋势——用一个统一模型替代多个专用工具。GitHub 开源（⭐85）。

arXiv 2507.06670 GitHub ⭐85

ACE-Step 1.5：双脑架构 + 完整数据处理工具链（GitHub ⭐11.9K，2025-2026）

ACE-Step 1.5 是目前最强大的开源本地音乐生成模型（超过几乎所有商业替代品）， 其数据处理工作也非常完善，提供了从数据准备到训练再到推理的完整工具链。

架构："双脑"设计
① 5Hz LM（规划器，可选）：通过 Chain-of-Thought 推断 BPM/调性/时长等元数据， 优化 caption，生成语义 codes（隐含旋律/编排/部分音色）。可选 0.6B/1.7B/4B 三个规模
② DiT（执行器）：接收 codes 和条件，通过流匹配扩散过程生成高保真音频

数据处理 Pipeline：
① 音频+歌词+标注三件套：每首歌需要音频文件（mp3/wav/flac/ogg/opus）、 .lyrics.txt 歌词文件、.json 标注文件（caption/bpm/keyscale/timesignature/language）
② 歌词转录：如无歌词，提供 Whisper / ElevenLabs Scribe 自动转录脚本（scripts/lora_data_prepare/）， 转录后必须人工审核修正。支持 LRC 格式歌词去时间戳
③ BPM/调性获取：推荐使用 Key-BPM-Finder（vocalremover.org）在线获取， 导出 CSV 批量导入。也可用 librosa 等 BPM 检测库
④ Caption 生成：使用 acestep-5Hz-lm 自动标注（Gradio UI Auto Label）， 或使用 Gemini API 批量生成 caption（gemini_caption.py）
⑤ 数据预处理：Gradio UI 可视化数据审核→预处理生成 .pt tensor 文件。 预处理需 12GB+ VRAM，将音频编码为模型训练用的 latent 张量
⑥ 训练：LoRA 微调（4x24GB 起步）或全参数 SFT（8x40GB 起步）。 支持多 GPU 训练

大规模训练数据：Muse 数据集
使用 Muse 数据集 （116K 首授权合成歌曲）进行大规模 SFT 训练。数据分中英文两部分（suno_cn_songs / suno_en_songs）， JSONL 元数据包含 song_id、audio_path、lyrics、caption、sections 等。 转换脚本 convert_muse_to_acestep.py 将 Muse 格式转为 ACE-Step 目录结构。
存储需求：音频 500GB + 预处理 tensor 800GB-1.2TB + checkpoint 50-200GB = 总计 1.5-2TB

推理端数据处理（关键创新）：
• Reference Audio（风格参考）：VAE tiled_encode 编码为 latent，时间维度取平均，全局控制音色/风格
• Source Audio（结构控制）：量化为 5Hz 语义 codes，保留旋律/节奏/和弦/编排，用于 Cover 模式
• audio_cover_strength：0.0-1.0 控制源音频结构保留程度
• Repaint：局部时间段重绘，保留上下文
• Extract：分轨提取（人声/伴奏分离）
• Vocal2BGM：从人声自动生成伴奏

其他技术特性：
• DCW（Differential Correction in Wavelet Domain）：训练无关的小波域微分修正， 解决扩散模型 SNR-t 偏差，按频带分别修正（CVPR 2026, arXiv 2604.16044）
• ALT_VAE：支持社区微调 VAE 替换（如 ScragVAE），改变音色/瞬态处理
• 支持 Mac/AMD/Intel/CUDA 全平台，2 秒生成一首完整歌曲（A100）

参考价值：ACE-Step 1.5 的数据处理工具链是开源项目中最完善的—— 从歌词转录、BPM 检测、Caption 生成、数据预处理到训练全流程覆盖。 其 5Hz 语义 codes 表征方式代表了一种全新的旋律控制范式：不使用 MIDI/符号曲谱， 而是让 VAE/DCAE 编码器自动学习音频到语义 token 的映射。

GitHub ⭐11.9K Muse 数据集 (116K songs) DCW paper (CVPR 2026)

推荐数据处理 Pipeline

基于以上调研，为"曲谱歌声合成 + 歌声克隆"目标推荐一套可落地的数据处理 pipeline。

推荐方案：结合 OpenVPI 社区工具链 + 学术界最新自动化方法， 构建"分离→对齐→MIDI提取→质量过滤"全自动 pipeline， 同时保留人工校验环节处理高质量子集。

推荐 1

人声分离：Demucs / UVR

使用 Demucs htdemucs 模型进行高质量人声分离。对于批量处理，可使用 UVR-GUI。 如果追求极致质量，可用 BS-RoFormer（MSST 项目）。分离后人声 SNR 应 > 20dB。

Demucs UVR-GUI
推荐 2

歌词对齐：MFA + MakeDiffSinger

使用 MFA 进行音素级强制对齐，配合 MakeDiffSinger 工具链配置歌声声学模型。 对于大规模无标注数据，可用 STARS 或 VocalParse 自动化对齐。 G2P 转换使用 OpenJTalk（日语）、pypinyin（中文）、g2p_en（英语）。

MFA MakeDiffSinger STARS VocalParse
推荐 3

旋律提取：SOME + FCPE/CREPE

使用 SOME（Singing-Oriented MIDI Extractor）直接提取 MIDI， 配合 FCPE 或 CREPE 提取逐帧 F0 轨迹。 SOME 专为 SVS 数据制作设计，可直接输出与歌词对齐的 MIDI。 节拍追踪使用 madmom 库。

SOME ⭐702 FCPE CREPE ⭐1.4K
推荐 4

质量过滤 + 人工校验

自动标注结果需要质量过滤：对齐置信度（MFA posterior probability）、 F0 连续性检查（过滤颤音区域异常）、SNR 评估、去重。 高质量子集（如 10%）进行人工抽检修正。 参考 DeepSinger 的多维度过滤策略和 SingNet 的质量评估 pipeline。

推荐 5

技巧标注（可选）：TechSinger 检测模型

如需技巧控制，使用 TechSinger 的技巧检测模型自动标注音素级技巧标签（7 种技巧）。 或参考 GTSinger 的 6 种技巧标注规范进行人工标注。

TechSinger GTSinger

总结与关键洞察

1. 数据制作正在从"人工标注"向"自动化歌声转谱"演进

DeepSinger（2020）开创全自动 pipeline → STARS（2025）统一框架 → VocalParse（2026）用音频大语言模型实现规模化转写。 趋势是用 LLM 统一多阶段 pipeline，减少对专用工具的依赖。

2. OpenVPI 社区提供了最完整的开源工具链

DiffSinger + MakeDiffSinger + SOME + OpenUtau 构成了从数据制作到合成再到编辑的完整生态。 对于想快速搭建 SVS pipeline 的团队，这是最佳起点。SOME（⭐702）专为 SVS 数据制作设计，是最实用的 MIDI 提取工具。

3. 旋律表征方式正在从"精细标注"向"灵活控制"演进

早期 SVS 需要音素级精确标注（方式①）→ RMSSinger 提出词级真实曲谱（方式②）→ SoulX-Singer 支持 MIDI+F0 双模式（方式③④）→ TokSing 用离散 token（方式⑤）→ YuE/DiffRhythm 不需要曲谱（方式⑥）→ YingMusic-Singer 用参考音频引导（方式⑦）→ UniVoice 统一语音歌声（方式⑧）。趋势是灵活控制 + 降低标注成本。

4. 对于"曲谱歌声合成+歌声克隆"目标的最佳实践

数据制作：路线 C（已有曲谱对齐）+ OpenVPI 工具链 = 最优成本效益
旋律表征：方式③（MIDI+预测）或方式④（F0直接输入），参考 SoulX-Singer 双模式
自动化补充：SOME 提取 MIDI + MFA 对齐 + STARS/VocalParse 自动标注
大规模扩展：Demucs 分离 + DeepSinger pipeline + SingNet 质量过滤
